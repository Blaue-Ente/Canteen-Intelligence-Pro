## 🎯 Каква е целта

Искаме да изградим **централен кодиращ AI агент** в ADN, който чрез mesh "тунел"
може да чете, анализира и да помага с поправки на кода във всичките 8 Iyveris
приложения **от едно място**, със специфичен режим за всяко приложение.

Това ще ни позволи:
- Бърза диагностика на проблеми между приложенията
- Координирани промени, които засягат повече от една услуга
- Централно управление без да отваряме 8 различни Replit проекта
- Автоматизирана поддръжка

## 🏛 Архитектура накратко

```
┌─ ADN — Code Agent Hub ─────────────────────┐
│  • UI с dropdown за избор на режим (8)     │
│  • LLM (Claude/GPT) — едно копие, в ADN    │
│  • Команден прозорец (естествен език)      │
│  • Бързи команди за всеки режим            │
│  • Conversation history + diff viewer      │
│  • Audit log + rollback                    │
└──────────────────┬─────────────────────────┘
                   │
                   │ POST /api/iyveris
                   │ X-Iyveris-Mesh-Key (стандартен)
                   │ X-Code-Agent-Token (НОВ, само за write/run)
                   │
                   ▼
┌─ В твоето приложение — Remote Agent ───────┐
│  Нов action в /api/iyveris: "code_op"      │
│  Изпълнява локални операции от whitelist   │
│  Връща резултат + diff                     │
└────────────────────────────────────────────┘
```

**Ключова идея:** LLM-ът живее **само** в ADN. Ти не трябва да имплементираш AI
от твоя страна. Ти си "механичните ръце" — приемаш конкретни операции и ги
изпълняваш в твоята среда.

---

## 🔧 Какво трябва да имплементираш

Един нов action `code_op` в твоя `/api/iyveris` handler.

### Структура на заявката

```json
POST /api/iyveris
X-Iyveris-Mesh-Key: <IYVERIS_MESH_KEY>
X-Code-Agent-Token: <CODE_AGENT_TOKEN>   // само при write/run!
Content-Type: application/json

{
  "action": "code_op",
  "payload": {
    "op": "read_file",      // вижте таблицата долу
    "path": "src/main.py",
    "content": "...",        // при write_file
    "command": "...",        // при run_command
    "lines": 200             // при get_logs
  },
  "from_service": "adn"
}
```

### Стандартен отговор

```json
{
  "ok": true,
  "result": { ... },
  "error": null
}
```

### Операции от whitelist (минимална имплементация)

| Operation | Нужен токен | Описание |
|-----------|-------------|----------|
| `read_file` | mesh само | Прочети съдържание на файл |
| `list_dir` | mesh само | Списък файлове в директория |
| `get_logs` | mesh само | Последни N реда от логовете |
| `get_status` | mesh само | Версия, uptime, известни грешки |
| `git_diff` | mesh само | Последните uncommitted промени |
| `write_file` | mesh + code_agent | Запиши съдържание (с автоматичен backup) |
| `run_command` | mesh + code_agent | Изпълни команда от whitelist |
| `restart_service` | mesh + code_agent | Рестартирай workflow |
| `rollback` | mesh + code_agent | Възстанови последния backup |

## 🔐 Изисквания за сигурност

Това е критично, защото даваме write достъп през мрежата.

### 1. Двойна автентикация
- `IYVERIS_MESH_KEY` (вече имаш) — за всички операции
- Нов `CODE_AGENT_TOKEN` (ще го добавим) — **само** за write/run/restart/rollback
- Read операциите минават само с mesh ключа

### 2. Whitelist на команди
`run_command` приема **само** предварително одобрени команди:
- `pnpm install`, `npm install`, `pip install -r requirements.txt`
- `pytest`, `npm test`, `pnpm test`
- `pnpm run build`, `pnpm run typecheck`
- Рестарти на workflows

**Забранено:** `bash`, `sh`, `eval`, `exec`, `rm -rf`, всякакви shell wildcards

### 3. File path whitelist
`write_file` приема само пътища **в** проекта:
- ✓ `src/main.py`, `components/Button.tsx`
- ✗ `.env`, `*.key`, `secrets/*`, `..`, абсолютни пътища, `/etc/*`

### 4. Audit log
Всяка операция → запис в `.agent-audit.log` с формат:
```
2026-05-16T12:34:56Z | adn | write_file | src/main.py | hash_before:abc | hash_after:def
```
Този файл **не трябва** да може да се променя или трие през агента.

### 5. Backup и rollback
Преди всеки `write_file`:
- Snapshot на стария файл в `.agent-backups/<timestamp>/`
- Запазваме последните 50 snapshot-а
- `rollback` възстановява последния snapshot

### 6. Read-only по подразбиране
Когато се отваря нов режим, той е в read-only mode. Write се активира с явно
потвърждение от страна на потребителя в UI на ADN.

## 📋 Какво ще ти бъде нужно конкретно

### Env variables за добавяне в deployment secrets

```
IYVERIS_MESH_KEY=<вече имаш>
CODE_AGENT_TOKEN=<ще го генерираме, общ за всички 8 приложения>
```

### Нови директории във вашия проект

```
.agent-backups/      # автоматично създавана, за rollback snapshot-и
.agent-audit.log     # write-once log файл
```

### Промяна в `/api/iyveris` handler

Добавяне на handling за `code_op` action — около 150-200 реда код в зависимост
от вашия стек.

## 🚀 План на изпълнение (фази)

Няма да внедряваме всичко наведнъж. Канарче подход:

1. **Фаза 1:** Изграждам централата в ADN с пълен достъп до ADN + read-only за останалите
2. **Фаза 2:** StockArgos получава remote агента първи (защото вече е тестван)
3. **Фаза 3:** Разпространение в 2-3 още приложения
4. **Фаза 4:** Финално разпространение в последните

Ти ще получиш сигнал когато е твой ред. Дотогава нищо не трябва да правиш.

## ❓ Какво искам от теб сега

Моля те да отговориш на следните въпроси:

### 1. Технически
- В какъв стек работиш? (Python/FastAPI? Node/Express? Друго?)
- Има ли вече handler за `/api/iyveris` mesh endpoint?
- Имаш ли вътрешен AI администратор/watchdog (като StockArgos)?
  Ако да — как взаимодейства с него?
- Какво е името на основния твой workflow за рестарт?

### 2. Архитектурни препоръки
- Виждаш ли проблем с предложената tunnel архитектура?
- Има ли операция, която мислиш че трябва да добавим в whitelist-а?
- Има ли операция, която предлагаш да премахнем?
- Препоръчваш ли допълнителни мерки за сигурност?

### 3. Специфики на твоето приложение
- Кои са най-критичните файлове, които **никога** не трябва да се пипат
  автоматично (дори с write достъп)?
- Има ли директории, които съдържат генериран код и не трябва да се
  редактират ръчно?
- Какъв е процесът ти за deploy след промяна на кода?
- Колко време отнема рестарт + warmup на твоето приложение?

### 4. Бързи команди
Кои са 3-5 най-полезни бързи команди специфично за теб?
(Примери от други приложения:
"Покажи последните грешки", "Тествай главния endpoint", "Провери базата данни"...)

## 📚 Допълнителен контекст

Този проект е базиран на pattern, който в индустрията се нарича
**"central orchestrator + remote execution agents"**. Подобен на това как:
- Ansible управлява remote сървъри
- Kubernetes управлява pods
- GitHub Actions runners изпълняват jobs

Разликата е, че нашият orchestrator използва AI за вземане на решения,
не статични playbook файлове.
